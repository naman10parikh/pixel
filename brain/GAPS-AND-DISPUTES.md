## §2 — [DISPUTE / JUDGMENT] shadcn primitives: Radix (now) vs Base UI (the signaled future)
- **Side A (stay Radix):** de-facto default, most-tested shadcn surface, unified `radix-ui` package = clean deps, `asChild` composition intact. Community migration guide #9562 has **34 👍 but 0 official comments** — momentum, not an official default.
- **Side B (go Base UI):** it's shadcn's *intended future* (CLI v4 already ships `--base base-ui`), from overlapping Radix/Floating-UI/MUI authors. But the move **removes `asChild`** (global refactor), changes forms (`Field`), and positioning (Floating UI → popover/tooltip behavior differs).
- **Why unresolved:** shadcn has signaled Base UI as the direction but has NOT made it the default style; the verdict is a reasoned recommendation, not a vendor default.
- **pixel's working posture (→ [[OPINIONS]] O3):** **Radix now, Base UI on the watch-list.** Re-evaluate the instant shadcn flips the *default* style to Base UI.
- **Probe to close:** watch `ui.shadcn.com/docs/changelog` for "Base UI is now the default style"; when it lands, scope the `asChild` migration cost (`grep -rc asChild src/`) before adopting. [ecosystem-03, ecosystem-10]

## §11 — [DISPUTE] Utility-first (Tailwind) vs vanilla/semantic CSS (the 2026 resurgence)
- **Side A — utility-first (Adam Wathan, Tailwind creator), verbatim:** *"When everyone on a project is choosing their styles from a curated set of limited options, your CSS stops growing linearly with your project size."* / *"Building things utility-first leads to more consistent looking designs than working component-first."*
- **Side B — the 2026 vanilla-CSS resurgence (Tobore/DEV, Mahnoor/Medium, solid-web), close-to-source:** *"CSS nesting is native now. No preprocessor needed… the 'readability' argument for Tailwind has vanished."* / *"While Tailwind's JIT compiler purges unused CSS, it doesn't solve HTML Bloat. Every utility class added is more bytes for the browser to parse in the DOM."* → claim *"Handcrafted CSS can load up to 30% faster on mobile"* (flagged vendor-adjacent, NOT independently benchmarked). Plus the "makes us bad developers" thesis (utilities atrophy CSS knowledge).
- **The honest middle (2026 consensus), verbatim:** *"both tools are genuinely good in 2026… the gap between them is the smallest it's ever been."* / *"Tailwind trades HTML readability for CSS consistency. Vanilla CSS trades setup speed for long-term flexibility. Neither tradeoff is universally right."*
- **pixel's working posture:** energy mandates Tailwind v4 and that's the right default for *velocity + a shared token vocabulary across an agent fleet* (the Wathan "curated set" is exactly what stops AI-generated CSS sprawling). But "Tailwind = always correct" is NOT a 2026 truth. **Dividing variable: team size + consistency need (Tailwind wins) vs bundle/DOM weight + single-author autonomy (vanilla wins).** For a tiny, perf-critical, single-author surface, native CSS (nesting + container queries + custom props) is a legitimate choice — and intersects [[OPINIONS]] O-F5 (native CSS now reaches higher).
- **Probe to close:** benchmark a representative pixel surface both ways (Tailwind v4 vs hand-CSS) for built-CSS size + DOM weight + INP; record which actually wins for which surface profile. [field-05 §1 / field-craft-04 (Wathan vs Tobore/Mahnoor/solid-web, 2026)]

## §12 — [DISPUTE] React Server Components / App Router: paradigm, or over-engineering?
- **Side A — RSC is over-engineered (HN #45755911, 119 pts), verbatim:** `hdjrudni`: *"I'm surprised so many people drank the RSC koolaid… how much harder it is to build something that used to be simple."* · `gherkinnn`: *"Next could've become JS' Rails, instead it is a pile of confusing mess… a conceptual mess of initialisms (RSC, SSR, PPR, SSG, ISG)… Next should no longer be chosen under any circumstances."* · `BoorishBears` (the sharpest): the real problem is *"under-engineering at the request layer 'forcing' massive over-engineering at the routing layer"* — fix it with a client data layer (TanStack Query) + loaders + tRPC, *"none of the benefits you're describing are tied to RSC."* · LogRocket (why Remix 3 dropped React): *"the amount of meta-knowledge required to set up a React project correctly is genuinely unreasonable for a lot of teams."*
- **Side B — RSC solves a real, hard problem, verbatim:** `Swizec`: independent components fetching their own data create *"lots of uncoordinated data fetches"* (waterfalls); the router is *"perfectly positioned to know what you're about to access"* → *"The biggest innovation in the past 5 years has been routers that can coordinate loading data."* · `pas`: Next *"rightfully dominates"* latency-optimized, highly-dynamic sites; *"it's messy now, but not that complicated… in a few revisions it'll likely look (and feel) more sleek."* · The State of React 2025 framing: React *"is here to stay"* as the default UI for AI-generated apps; both Next and TanStack Start ship RSC.
- **The synthesis nobody fully states:** the fight is about WHERE coordination lives — a client data layer (TanStack Query) + typed RPC vs the router-as-coordination-point with RSC making it free. Both build working apps; the cost is complexity vs infra/payload. RSC is also a *"poor fit for interfaces dominated by continuous client-side interaction, such as complex dashboards, design tools, or real-time collaborative environments."*
- **pixel's working posture:** default to App Router/RSC (energy + Next 16 momentum) for content/marketing/dashboards-with-server-data. But **never treat "use the App Router" as unquestionable** — for highly-interactive, client-state-heavy surfaces (editors, optimistic-UI dashboards, realtime) a SPA/client-data-layer (TanStack Query/Router, or TanStack Start) is *legitimately better, not heresy*. **Dividing variable: content/navigation-heavy (RSC pays off) vs continuous client interaction (RSC is overhead).** Cross-ref the migration footgun: App Router's multi-layer caching → "stale inventory after deploy" ([[KNOWN-PITFALLS]] §5, [[BATTLE-TESTED-SCENARIOS]] S17). [field-05 §3 + field-craft-04 §1 (HN #45755911 verbatim; State of React 2025 via devclass 2026-02-18; LogRocket Remix 3)]

## §13 — [DISPUTE] Tailwind itself: safe foundation, or a project at risk? (OSS-funding canary)
- **Side A — adoption/safety:** Tailwind = ~75M monthly npm downloads, 51% of web projects (2025 State of CSS); the v4 Oxide engine is fast; it's the de-facto standard and won't vanish.
- **Side B — sustainability risk (byteiota 2026-05-17), verbatim:** Jan 2026 Tailwind Labs cut **3 of 4 engineers (75%)**. Wathan: *"Tailwind is growing faster than it ever has… and our revenue is down close to 80%."* Cause: AI assistants answer in-editor, killing the docs→Tailwind-UI ($299) discovery funnel — *"documentation traffic fell 40% since early 2023 while usage grew every quarter."* Vercel + Google AI Studio gave post-layoff sponsorship; the structural issue is unresolved.
- **pixel's working posture:** Tailwind is **safe to BUILD on** (huge install base) but **maintenance velocity may slow** and the paid products (Tailwind UI/Catalyst) are the uncertain part. This is an OSS-economics canary, NOT an imminent-death signal — and it's the same AI-killed-the-docs-funnel dynamic that will hit other dev-tool OSS. **Re-check quarterly.**
- **Probe to close:** quarterly — Tailwind Labs headcount/release cadence + whether v4.x point releases keep landing; if cadence stalls >2 quarters, escalate the "pin a known-good version" posture. [field-craft-04 §4 / field-craft-06 §6 (byteiota 2026-05-17; Wathan revenue quote)]

## §14 — [DISPUTE] Component ownership: copy-paste (shadcn) vs installed dependency (MUI/Mantine)
- **Side A — copy-paste (shadcn camp):** copy components into your repo → you OWN the code, AI agents modify it directly, no black-box deps (energy bible: "code ownership > npm").
- **Side B — installed lib (HN `Shorn`), verbatim:** *"MUI for the component library… plus Playwright… this stack, plus claude-code… is a literal productivity super-power. You can crank out entire complicated LoB apps."* Argues a batteries-included *installed* lib + AI ships line-of-business apps faster than hand-owning every component.
- **pixel's working posture:** depends on surface. **Design-differentiated product (pixel's flagship case) → shadcn copy-paste** (control over the craft layer is the whole point). High-volume internal CRUD/LoB → an installed lib may ship faster; don't sneer at MUI+AI, it's a real datapoint. **Dividing variable: craft differentiation needed (shadcn) vs CRUD-volume velocity (installed lib).** Note the related contested fact that even shadcn's *primitive* is in flux (Radix→Base UI, §2). [field-craft-04 §5 (HN `Shorn`; shadcn copy-paste vs MUI-installed)]
